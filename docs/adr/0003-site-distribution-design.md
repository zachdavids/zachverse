# ADR 0003: Site distribution design

- Status: Accepted (synthesized; not yet deployed)
- Date: 2026-10-11, revised 2026-10-12 after review and 2026-10-13 for the identity stack (ADR 0004), the certificate, and the guardrails in every synthesis

## Decision

`ZachverseSite` (us-east-1) contains a private S3 bucket, an origin access control, one CloudFront Function, one distribution, and `SiteDeployPolicy`, the GitHub deploy role's permissions (ADR 0004). When `pricingPlan` is configured it also contains a pricing-plan subscription.

- **Bucket:** Block Public Access on, bucket-owner-enforced ownership, SSE-S3, a TLS-only policy, no static website hosting. Versioning is on, and noncurrent versions expire after 90 days, so files overwritten by a release can be recovered. A separate rule aborts multipart uploads still incomplete after 7 days: a cancelled or timed-out deploy job kills the AWS CLI before it can abort its uploads, and S3 bills the parts until they are aborted. That rule deletes no objects.
- **Origin access:** the S3 REST endpoint through OAC (SigV4, always). The bucket policy allows only `s3:GetObject` and `s3:ListBucket` to `cloudfront.amazonaws.com`, conditioned on this distribution's ARN. `ListBucket` makes S3 return 404 rather than 403 for missing keys.
- **Errors:** only 404 is mapped, to `/404.html` with status 404 and a 60-second error cache. 403 is left unmapped so real access failures stay visible.
- **Behavior:** one default behavior with HTTPS redirect, `index.html` as the default root object, and AWS-managed `CachingOptimized` and `SecurityHeadersPolicy`. The redirect is set explicitly; `cdk.json`'s HTTPS-by-default CloudFront flag also makes it CDK's default for any behavior added later. The managed policy's HSTS has no `includeSubDomains`. HTML freshness comes from per-object `Cache-Control` set at upload (milestone 6).
- **Viewer-request function** (`cloudfront-js-2.0`): redirects `www.zachdavids.com` to the apex with a 301, keeping path and query. Directory-style paths map to `index.html`; `/.well-known/` is left alone.
- **Hostnames:** `zachdavids.com` and `www.zachdavids.com`, with the out-of-band certificate requested on 2026-10-13, whose validation CNAMEs are the committed batch `infra/dns/2026-10-13-acm-validation.json` (ADR 0002). TLS 1.2_2021, SNI, IPv6, HTTP/2 and HTTP/3. `certificateArn` in `infra/lib/config.ts` is required: synthesis fails on an empty one, or on any ARN other than `arn:aws:acm:us-east-1:<configured account>:certificate/<lowercase UUID>`, so a bad paste fails before deployment.
- **Retention:** every resource the stack defines has `DeletionPolicy` `RetainExceptOnCreate` and `UpdateReplacePolicy` `Retain`. Each is kept when the stack is deleted, when it leaves the template, and when it is replaced, and is deleted only if the operation that created it rolls back, so a failed first deploy leaves no orphaned, fixed-name function or OAC to block the retry. Tests pin logical IDs and create-only properties. CDK version reporting stays on (AWS uses it to contact users of CDK releases with serious security or reliability issues): the CLI turns it on, so the template also gets an `AWS::CDK::Metadata` resource. That resource creates nothing in the account (it carries only the version-reporting record), so it is not retained.
- **Termination protection:** on. The CDK CLI turns it on before the first create runs, and it stops the CLI from deleting a stack whose create failed. To retry a failed first deploy, turn protection off and deploy again; the CLI then deletes the failed stack and turns protection back on. The CLI also turns protection on before it asks to approve IAM changes, so a first deploy whose approval is refused, or that cannot ask because it has no terminal, leaves an empty `ZachverseSite` in `REVIEW_IN_PROGRESS`, and the CLI's cleanup fails with CloudFormation's termination-protection error. Deploying again with `--require-approval never` (ADR 0004, "Runbook") creates the resources in that stack; to abandon it instead, turn protection off and delete it.
- **Free flat-rate plan (off by default):** `pricingPlan: { tier: 'FREE', webAclArn }` sets the distribution's `WebACLId` and adds `AWS::PricingPlanManager::Subscription`. That subscription is `CloudFront`/`FREE` over the distribution, the web ACL, and `arn:aws:route53:::hostedzone/Z03492543O0YEY0RDZZ0J`. Paid tiers are not representable in config. Synthesis fails on a `webAclArn` other than a CLOUDFRONT-scope web ACL owned by the configured account, `arn:aws:wafv2:us-east-1:<account>:global/webacl/<name>/<lowercase UUID>`.

## Template checks (`infra/lib/guardrails`)

The template rules are in `infra/lib/guardrails/checks.ts`, summarized here:

- **Prohibited resources:** no hosted zones, Route 53 records or domains, Amplify domains or Cloud Map resources (both write DNS themselves), Cognito resources (an identity pool could exchange GitHub tokens for credentials), custom resources, Lambda functions, CloudFormation-managed certificates, or StackSets.
- **Template indirection:** no nested stacks, `AWS::ServiceCatalog::` resources, or other `AWS::CloudFormation::` types; no `Transform` or `Fn::Transform`; and no resource types outside `AWS::`.
- **No DNS write access:** no IAM permission that can write Route 53 or Route 53 Domains, wildcards included. The check fails closed: a grant it cannot read, such as `NotAction`, a computed action or document, a managed policy or group from outside the stack, or an Identity Center resource, fails too. It can allow CNAME CREATE/UPSERT on the exact ACM validation names in this zone, through the literal `route53:ChangeResourceRecordSets` action, but no stack gets that allowance: validation is out of band (ADR 0002).
- **Retention:** every resource retained (`DeletionPolicy` `Retain` or `RetainExceptOnCreate`, and `UpdateReplacePolicy` `Retain`) except `AWS::CDK::Metadata`.
- **Free-plan compatibility**, per the [flat-rate plan page](https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/flat-rate-pricing-plan.html) (read 2026-10-12): at most 5 cache behaviors and 5 web ACL rules, only AWS-managed cache, origin-request, and response-header policies, and none of the CloudFront or WAF features or associations that the plan does not support, such as logging, Origin Shield, mutual TLS, rule groups, CAPTCHA, or a function or web ACL shared with another distribution.
- **Project rules**, which the plan does not impose: no Lambda@Edge (the plan allows it on every tier but bills it outside the flat rate), and CloudFront Functions on `cloudfront-js-2.0`, defined in the stack so their runtime can be checked.
- **GitHub trust and deploy permissions:** ADR 0004 gives these rules and their limits.

They run in every synthesis of the app, not only in the tests:

- **In every synthesis.** `createStacks` registers a CDK validation plugin (`infra/lib/guardrails/plugin.ts`) that applies every rule to every stack template the synthesis writes, wherever its stack is (inside another stack, a Stage, or a plain construct), and checks that each stack targets account `426499248998` and Region `us-east-1` with termination protection. A nested stack's template is written as an asset, which CDK does not pass to the plugin, so the rule against nested stacks rejects the parent's `AWS::CloudFormation::Stack` resource instead. Every violation is fatal, so no acknowledgment can suppress it, and names its rule, its resource or stack, and its template. An error inside the plugin fails the report too. The plugin is registered while CDK validates the construct tree, after CDK creates each stack's version-reporting resource, which lists the validation plugins registered at that moment: registered earlier, the plugin would be listed there and change the deployed identity stack's template.
- **Under the CDK CLI.** The CLI tells every app not to fail on validation errors. The commands that validate the stacks, such as `synth`, `diff`, and `deploy` (not `list` or `destroy`), fail on the recorded report instead, unless `--ignore-errors` or `CDK_IGNORE_ERRORS` is set. They drop the violations in stacks the command does not select, and read a report left with none, such as a failed plugin's, as a pass. So `bin/zachverse.ts` turns failing back on through `postCliContext`, which outranks the CLI's context and `cdk.json`'s, and the app fails its own synthesis on any violation or plugin error. Every CLI command that synthesizes the app then fails, whatever its flags or context: `cdk list` and `cdk destroy` too, and a synth or deploy of `ZachverseIdentity` alone.
- **In the tests.** CI and `cdk.json`'s `build` step also run the rules in Vitest, on both stacks with the site certificate and with the pricing plan off and on, and the entry-point test shows `bin/` failing under the CLI's context.

`infra/test/checks.test.ts` feeds each check deliberately offending stacks and templates to show that it fails. On 2026-10-11 the guardrail suite was also run once against a temporarily mutated `site-stack.ts`. The mutation added auto-emptying of the bucket, removed the bucket's retention, and added an apex `A` record. The suite flagged `Custom::S3AutoDeleteObjects`, its Lambda handler, the `AWS::Route53::RecordSet`, and the non-retained bucket; the mutation was then reverted.

## Limits

Passing these checks says nothing about live resources, IAM in the account, the effect of the managed SCPs, whether the certificate is issued (synthesis checks only its ARN's form), or whether the pricing-plan service accepts the configuration. Milestones 4–7 verify those against the deployed site stack; ADR 0004 records the identity stack's live state, and its runbook waits for the certificate to be `ISSUED` before the first site deployment, since CloudFront rejects one still pending validation. The checks also have limits of their own:

- These are template checks, not access controls. CloudFormation deploys every stack through the CDK execution role, which can write DNS (ADR 0002). `--build ''` (or `CDK_BUILD=`) skips only the typecheck and the tests, not the plugin. What still gets past the checks:
  - **Changed code.** A commit that weakens the rules, the plugin's registration, or `bin/`'s `postCliContext` also passes them, and so does synthesizing with construct validation skipped (`app.synth({ skipValidation: true })`), which never registers the plugin. So deploy only reviewed commits.
  - **An assembly synthesized earlier**, passed with `--app <dir>` (such as `cdk.out`). No app runs, so nothing checks its templates except the CLI's reading of its `validation-report.json`. That refuses the assembly only when its report records a violation in a stack the command selects, unless `--ignore-errors` or `CDK_IGNORE_ERRORS` is set. A report from a plugin that failed (it has no violations), violations only in stacks the command does not select, a deleted or edited report, or an assembly from code without the plugin gets past it.
  - **Environment variables and user settings.** The CLI reads every option from any environment variable whose name starts with `CDK` (`CDK_APP`, and also `CDKAPP`), so `CDK_APP`, `CDK_BUILD`, and `CDK_IGNORE_ERRORS` act like `--app`, `--build`, and `--ignore-errors` with nothing on the command line, and `CDK_PLUGIN` loads code into the CLI. It also merges the user's `~/.cdk.json` under `cdk.json`, so that file can set whatever `cdk.json` leaves open; `cdk.json` pins version reporting on and an empty plugin list, which `~/.cdk.json` cannot override. ADR 0004's runbook checks that no such variable is set and that the file does not exist.
- The checks read only what synthesis produces, so a resource that runs code or launches another template during deployment is outside them unless a rule names it.
- The template rules run in the CLI's own synthesis, whatever its input or timing, but the assertions that run only in Vitest do not: the stacks' design tests, the logical-ID and create-only pins, the identity template pin, and the comparison of `bin/`'s cloud assembly with the checked app's. Under the CLI the app gets input the tests do not give it, and synthesizes once the event loop is empty, later than the tests synthesize it (the entry-point test waits about one turn). So a change anywhere in the app, `lib/` as well as `bin/`, can still change what the CLI deploys without failing those assertions if, for example, it depends on input only the CLI gives (`-c` context, `cdk.context.json`, a context key such as `aws:cdk:enable-path-metadata`, or an environment variable such as `CDK_CLI_VERSION`), runs in work deferred past the point where the tests synthesize (a timer of a few milliseconds or more, or I/O that finishes after it), or is keyed to how the app is run (`require.main`, `process.argv`, or a variable only Vitest sets, such as `VITEST`).
- The DNS check does not model privilege escalation, such as `iam:PutRolePolicy` or `sts:AssumeRole` into a role that can write DNS.
- The Free-plan checks look for shared functions and web ACLs only among one template's distributions, and read a web ACL only when a stack defines it, so milestone 7 must confirm that the web ACL fits the plan and that no other distribution uses it or the viewer-request function.
- The viewer-request tests approximate the `cloudfront-js-2.0` runtime on V8, with a reduced set of built-ins and a syntax allowlist, so they cannot catch where the runtime and V8 behave differently (the runtime's regular expressions are PCRE, for example). Nor can they catch a built-in the runtime lacks that is used only on a path no test runs, or one the tests keep on every path: a member keyed by a symbol, or a well-known symbol (`[Symbol.iterator]()` or `Symbol.asyncIterator`, for example). The header comment in `infra/test/viewer-request.test.ts` gives the details.
